The Core Mental Model: "The Castle"

Before any security group or subnet, internalize one idea: AWS networking is a series of nested boundaries, and every connection must be explicitly allowed in the direction it flows.

Think of your VPC as a medieval castle:

Outer courtyard (visible from road)Public subnetHas a route to the internet gateway; things here can have public IPs

The one question that solves everything: For any two components, ask "Does A need to initiate a connection to B? On what port? In which direction?" Each "yes" becomes exactly one security group rule. That's it. Security groups are not mysterious - they are just the written-down answers to that question.

Layer 1 - Network Topology: Who Goes Public, Who Goes Private

The guiding principle for placement: A component goes in a public subnet ONLY if it must be reached directly from the internet, OR if it must be the "jump point" to reach private things. Everything else goes private, minimizing the public surface - minimizing attack surface. This is the single most-tested idea in a DevOps architect course.

Public Subnet (the courtyard - minimal, exposed on purpose)

ComponentWhy public
ALBUsers on the internet hit it directly. It's the front door. (It only needs public subnets; the LB itself is a managed service.)
Bastion host (Jump box)You (the admin) SSH into it from the internet, then hop to private instances. It's the controlled entry door.
NAT GatewayMust live in a public subnet to forward private instances' outbound traffic to the IGW.

Private Subnet (the keep - everything that does real work)

ComponentWhy private
App servers (EC2)Users never connect to them directly - only through the ALB. Keep them hidden.
Jenkins master + slaveCI/CD internals. No reason for the internet to reach them. (You access the UI via Bastion tunnel or VPN.)

SonarQube serverInternal code quality server.

RDSDatabase - the crown jewels. Never public.

S3 is special - It's not in your VPC at all. It's a regional AWS service reached either over the internet (via NAT) or, better, via a VPC Gateway Endpoint (a private tunnel from your VPC to S3 that never touches the internet). We'll revisit this in Layer 7.

Bastion vs NAT (The two pieces that confuse everyone)

They sound similar ("both are in public subnets, both bridge public and private") but they are opposites in direction:

BASTION -> INBOUND door for admins:   You (Internet) --SSH--> Bastion --SSH--> Private EC2
NAT GW  <- OUTBOUND door for servers: Private EC2 --yum/apt/docker pull--> NAT --> Internet

Bastion lets humans get in to manage private boxes. NAT lets private boxes get out to download packages/pull Docker images - while blocking anyone from using that same path to get in. Your private app servers need NAT so Jenkins/Docker can docker pull the image from Docker Hub, and so yum update works. But NAT guarantees no outsider can ride that connection backwards.

High Availability note (course graders love this)

Spread across 2 Availability Zones. So really: 2 public subnets (one per AZ) - ALB spans both, NAT in each (or one to save cost). 2 private subnets (one per AZ) - App servers spread across both; RDS Multi-AZ.

Layer 2 - How the ALB Reaches a Private Server (The key insight)

The confusion comes from a hidden assumption: "To reach a server, you need its public IP." That's true for the public internet, but false inside a VPC. Here's the correction:

Insight: Inside a VPC, everything talks via PRIVATE IPs
Every instance in your VPC gets a private IP (e.g., 10.0.3.47) regardless of subnet. Within the VPC's CIDR (10.0.0.0/16), any instance can route to any other instance's private IP - the VPC is one big internal network. Public IPs are only needed to cross the IGW to the internet. They are irrelevant for internal VPC-to-VPC traffic.

So the app server having no public IP doesn't matter - the ALB reaches it by its private IP, over the internal VPC network. The private subnet just means "no route to the internet gateway," not "unreachable from inside."

The chain, step by step

  1. User's browser --> DNS resolves your ALB's public DNS name (e.g. shop-alb-123.us-east-1.elb.amazonaws.com)
  2. Request hits the ALB (ALB lives in the PUBLIC subnet, has public-facing nodes). User <-> ALB connection terminates HERE. The user never sees what's behind.
  3. ALB consults its TARGET GROUP. A Target Group is just a LIST of registered targets: app-server-1 @ 10.0.3.47 : 8080 (Healthy), app-server-2 @ 10.0.4.88 : 8080 (Healthy)
  4. ALB opens a BRAND-NEW connection to one healthy target's PRIVATE IP:8080. This hop is entirely INSIDE the VPC = private IP is enough. This is ALLOWED because the app server's security group says: "Allow inbound :8080 FROM the ALB's security group."
  5. App server processes, replies to the ALB (stateful = reply auto-allowed).
  6. ALB relays the response back to the user.

The mental model shift

The ALB is a two-faced proxy:

   PUBLIC FACE                    PRIVATE FACE
   (listener)                     (Target group)
 ----------------              -------------------
| User--> :443   |             | --> 10.0.3.47:8080 |
| public DNS     |  (relays)   | --> 10.0.4.88:8080 |
 ----------------              -------------------
        ^                               ^
  Internet side                 VPC-internal side
  (needs public)                (private IP is fine)

The user's connection stops at the ALB. A second, independent connection goes from the ALB to the private target. The private subnet never touches the internet - the ALB is the bridge. This is exactly why private app servers are both reachable AND safe.

The two things that make the hop work

Target Group registration - the app server (its private IP + port) MUST be registered as a target. (In autoscaling setups the ASG auto-registers new instances; manually you add them.)

Security group rule - this is the elegant part. You don't hard-code the ALB's IP. You write: App-Server-SG: Allow inbound TCP :8080 from source = ALB-SG

Referencing one SG as the source in another SG means "Any instance wearing the ALB security group may enter." Clean, and it survives IP changes. This SG-referencing-SG pattern is the professional way and graders look for it.

Three principles baked into that table

  • SG references SG, never raw IPs (except bastion's /32 and ALB's 0.0.0.0/0). This is the hallmark of a professional design - it's self-healing when IPs change.
  • Least privilege - RDS accepts port 3306 only from app-sg/redis-sg, nothing else. No port is open "just in case."
  • Bastion is the ONLY box with SSH from the internet, and only from your IP. Every other SSH rule sources from bastion-sg or ansible-sg. This is the "single hardened entry point" pattern.
A subtle trap to notice: Look at app-sg: it has no inbound rule from the internet at all - not even port 8080 from 0.0.0.0/0. The only way traffic enters is via alb-sg. That's precisely what makes "private app servers behind an ALB" secure. If you ever find yourself adding 0.0.0.0/0 to app-sg, you've broken the model.

Layer 4 - Health checks: How the ALB knows a Server is alive

The problem health checks solve: The ALB has a list of targets (10.0.3.47:8080, 10.0.4.88:8080). But what if one app server crashes, or its container is mid-restart during a deploy? If the ALB blindly forwards a user to a dead server, the user gets an error. Health checks are the ALB continuously asking each target "are you OK?" and routing traffic ONLY to the ones that answer correctly.

The mechanism

The ALB (via the Target Group's health-check config) does this on a loop, per target:

Every 10s: ALB --GET http://10.0.3.47:8080/health--> app server
<-- 200 OK -------------------------------------- Healthy (keep routing)
<-- 500 / timeout / no answer ------------------- Unhealthy (stop routing)

You configure these knobs on the Target Group:

SettingTypical valueMeaning
Health check path/health or /actuator/healthThe URL the ALB pings
Port8080 (traffic port)Where to ping
ProtocolHTTP
Healthy threshold22 consecutive passes = mark healthy
Unhealthy threshold33 consecutive fails = mark unhealthy
Interval30sHow often to ping
Timeout5sHow long to wait for a reply
Success codes200What counts as "healthy"

Why this is deeply important for your CI/CD deploys

Here's the connection to your Jenkins pipeline that most people miss. When Jenkins deploys a new image to app server 1:

  1. New container starts on app-server-1 -> takes ~20s to boot the JVM
  2. During boot, /health returns 503 (app not ready) -> ALB marks it UNHEALTHY
  3. ALB routes ALL users to app-server-2 (still healthy on old version) -> ZERO downtime
  4. app-server-1 finishes booting -> /health returns 200 -> ALB marks HEALTHY again
  5. Jenkins then deploys to app-server-2, same dance.

This is a rolling deployment - and health checks are what make it safe. Without them, the ALB would send users to a half-booted server. So the health check isn't just monitoring; it's the traffic gate during deployments.

The app must EXPOSE a health endpoint

This is why - when we get to the code - your Java app will have a /health (or Spring Boot Actuator's /actuator/health) endpoint. The health check is a contract between your code and your infrastructure. A good /health endpoint ideally checks downstream dependencies too:

GET /health -> { "status": "UP", "db": "UP", "redis": "UP" } -> 200
                 (if DB is unreachable)                      -> 503

That way, if an app server loses its DB connection, the ALB stops sending it traffic automatically.

The one subtlety (SG dependency): For health checks to work, remember app-sg MUST allow inbound 8080 from alb-sg - the same rule that handles user traffic also lets the health-check probe through. One rule, two purposes. If you ever see all targets "unhealthy," the first thing to check is that SG rule.

Layer 5 - The Jenkins CI/CD flow

Core idea first: CI/CD is just a relay race. Jenkins is the coordinator standing in the middle; it doesn't do the work itself - it tells each specialist tool to run, waits for a pass/fail, and only hands the baton forward if the previous runner succeeded. Your tools (Maven, Sonar, Trivy, ECR) are the runners. Jenkins holds the stopwatch.

You described two phases, which is exactly right and a very mature design - separate "build & push" from "deploy." Let me show why that separation matters, then the full stage flow.

Why split into two phases (CI vs CD)

CI PHASE (Integration): code -> test -> quality -> scan -> BUILD IMAGE -> PUSH to registry
Produces an ARTIFACT (the image). Does NOT touch production.

CD PHASE (Deployment): PULL image from registry -> deploy to app servers
Consumes the artifact. Touches production.

The artifact (a tagged image in ECR/Docker Hub) is the clear handoff point. Benefits:

  • You can deploy the exact same tested image to staging, then prod - no rebuilding (rebuilding risks "works in staging, breaks in prod").
  • You can roll back by just re-deploying an older image tag.
  • The image is immutable - tagged with the build number/git SHA, so you always know exactly what's running.

The critical design decision: How does Jenkins deploy to private app servers?

There are two schools:

Option A - Jenkins SSHes directly to app servers (simpler, common in courses)
app-sg allows 22 from jenkins-sg.
Jenkins runs ssh appserver "docker pull && docker run".

Option B - Jenkins hands off to Ansible (cleaner, matches your plan since you want a separate Ansible server)
Jenkins calls the Ansible server; Ansible SSHes to app servers and runs the deploy playbook.
app-sg allows 22 from ansible-sg (which we already have).
Separation of concerns: Jenkins = orchestration, Ansible = configuration/deployment.
Since you explicitly want a dedicated Ansible server, Option B is the right fit - and it's what we'll detail in Layer 6.

One security note on ECR: When an app server does docker pull from ECR, it needs AWS credentials. DO NOT put access keys on the instance. Attach an IAM Role to the app-server EC2 (an "Instance Profile") granting ecr:GetDownloadUrlForLayer, ecr:BatchGetImage, etc. The instance then authenticates automatically. (Same IAM-role pattern will apply to S3 access later.) This "IAM roles not hardcoded keys" point is heavily graded.

Layer 6 - Ansible: Configuring Private Instances from a Dedicated Server

Core idea: Ansible is agentless push-based configuration. Unlike tools that need an agent installed on each target, Ansible just needs SSH access + Python on the targets. The Ansible server (the "control node") pushes instructions out over SSH. There's nothing to install on the targets beyond Python (which comes with the OS).

Why a SEPARATE Ansible server (your explicit requirement)

You said you want a dedicated Ansible server, not running on the bastion. The reasoning (good to articulate in your course):

ConcernBastion hostDedicated Ansible server

Putting your deployment SSH keys (which can touch every private server) on the internet-facing bastion is a security smell. A dedicated private Ansible server keeps those powerful keys off the exposed box. That's the architectural justification.

How Ansible reaches private targets - the connectivity

Ansible server is in a private subnet. Its targets are also private. Same-VPC = private-IP routing works (Layer 2 insight again). The SG rules we already wrote make it work:

  • app-sg allows 22 from ansible-sg √
  • jenkins-sg allows 22 from ansible-sg √
  • tools-sg allows 22 from ansible-sg √

You reach the Ansible server itself via the bastion (ansible-sg allows 22 from bastion-sg), then run ansible-playbook.

The three Ansible building blocks

1. INVENTORY (inventory.ini) - WHO to configure, grouped:

[app_servers]
10.0.3.47
10.0.4.88

[jenkins]
10.0.3.10

[all:vars]
ansible_user=ec2-user
ansible_ssh_private_key_file=~/.ssh/deploy_key.pem

2. PLAYBOOK (deploy.yml) - WHAT to do (declarative, idempotent):

- hosts: app_servers
  tasks:
    - name: Ensure Docker is installed
    - name: Log in to ECR
    - name: Pull image myapp:{{ build_number }}
    - name: Stop old container
    - name: Run new container

3. ROLES - reusable bundles of tasks (optional, for larger setups).

The key property: Idempotency
Ansible playbooks are declarative - you describe the desired end state, not the steps. "Ensure Docker is installed" = if already installed, Ansible does nothing; if not, it installs it. Running the same playbook twice is safe and produces the same result. This is why Ansible is used for both initial setup and repeated deploys.

How this plugs into Jenkins (the handoff)

Your CD phase, Option B from Layer 5. Jenkins CD stage:

sshagent -> ssh ansible-server \
  "ansible-playbook deploy.yml -e build_number=${BUILD_NUMBER}"

Ansible server then: SSHes to each app server (one at a time), pulls myapp:${BUILD_NUMBER} from ECR, swaps the container, moves to next server (rolling deploy).

So the full chain of trust: Jenkins -> (SSH) -> Ansible server -> (SSH) -> app servers. Jenkins never touches the app servers directly; Ansible is the sole deployment hand. Clean separation.

What Ansible configures in the initial setup (vs ongoing deploys):
Initial (run once per server): Install Docker, configure the OS, set up log forwarding, install the CloudWatch agent, harden SSH.
Ongoing (every deploy): pull new image, restart container.

Layer 7 - The Data Layer: RDS, Redis, and S3

Three different kinds of "storage," each solving a different problem. The mistake beginners make is treating them as interchangeable. Let me separate their purposes first.

StoreHoldsAccess patternWhy
RDS (MySQL/Postgres)Structured, relational data: users, orders, product records, pricesRead + write, must be durable & consistentSource of truth
RedisTemporary copies of frequently-read data; sessionsVery fast read/write, in-memory, can be lostSpeed
S3Large binary blobs: product imagesRead-heavy, served to usersCheap, scalable object storage

Why Redis sits "between" app servers and RDS (the caching pattern)

You asked specifically about this. The reason is RDS is relatively slow and expensive per query; Redis is in-memory and ~100x faster. For an eCommerce site, the same product ("iPhone 15, $999, 20 in stock") gets read thousands of times but changes rarely. Hitting RDS every time wastes it.

The pattern is cache-aside (lazy loading):

flowchart TD App[App Server needs product #42] --> RCheck{Check Redis first} RCheck -->|HIT: Returns instantly| Done[Done. RDS untouched] RCheck -->|MISS| RDS[App queries RDS] RDS -->|Returns product| RSet[App sets product in Redis TTL=5min] RSet --> AppRet[App returns product]

Next 1000 requests for product #42 -> all HIT Redis -> RDS load drops ~99%.

So Redis isn't literally a network hop in the middle - the app talks to both. Redis is "in between" logically: the app checks Redis first, falls back to RDS. Mental correction worth internalizing: the app orchestrates the cache; Redis doesn't proxy to RDS. Redis has no idea RDS exists.

This is why in Layer 3, both redis-sg (6379 from app-sg) and rds-sg (3306 from app-sg) source from the app servers - the app connects to each independently.

Why RDS and Redis are BOTH private

Neither should ever have a public IP. The database is your crown jewels; the cache may hold session tokens. Only app-sg can reach them. RDS also uses a DB Subnet Group (a set of private subnets across AZs) so it can do Multi-AZ failover - a standby replica in another AZ that takes over if the primary dies.

S3 - the odd one out (not in your VPC)

S3 isn't an EC2 or a subnet thing - it's a regional AWS service with its own endpoint. Your product images live there because:

  • Storing images in RDS is a classic anti-pattern (bloats the DB, slow, expensive).
  • Storing images on the app server's disk breaks when you have multiple app servers (image uploaded to server 1 isn't on server 2).
  • S3 is shared, durable, infinitely scalable - all app servers see the same images.

Two ways the app reaches S3 (an important design choice):

  1. App -> S3 via NAT Gateway (traffic leaves VPC, goes over AWS network to S3) - Works, but incurs NAT data charges and leaves the VPC.
  2. App -> S3 via VPC GATEWAY ENDPOINT (BETTER) - A private route from your VPC directly to S3. Never traverses the internet or NAT. Free, more secure. You add a route in the private subnet's route table pointing S3's prefix-list to the endpoint.

Graders love the VPC endpoint answer because it's the secure + cost-optimal choice.

How the app authenticates to S3: same IAM-role pattern as ECR - attach an IAM Instance Profile to the app servers granting s3:GetObject (and s3:PutObject if users upload images) on your bucket. No access keys in code.

How images actually get served (a common confusion)

Two models:

  • App proxies the image: user -> ALB -> app -> S3 -> app -> user. Simple, but app does heavy lifting.
  • Pre-signed URL / CloudFront (better): app generates a temporary signed S3 URL (or a CloudFront CDN URL), returns it to the browser, and the browser fetches the image directly from S3/CloudFront. App never touches the image bytes. Scales far better.

For your course, mention the pre-signed URL / CloudFront approach as the production-grade answer.

That completes the conceptual architecture. You now have the full mental model: network -> traffic -> security -> health -> CI/CD -> config -> data.

Breadth - From Static EC2 to an Auto Scaling Group

The problem ASG solves: Right now you have fixed app servers - say two, with hand-written private IPs in the ALB target group and the Ansible inventory. Two failures hide here: If one server dies, you're down to one until a human notices and rebuilds it. If traffic spikes (a sale), two servers can't cope, and if traffic is quiet at 3 AM you're paying for idle servers.

An Auto Scaling Group (ASG) makes the fleet elastic and self-healing: it maintains a desired count of identical servers, replaces dead ones automatically, and grows/shrinks with load.

The key mental shift: from "pets" to "cattle"

PETS (what you have now)CATTLE (what ASG gives you)
Named servers: app-srv-1,2Anonymous, interchangeable instances
Hand-configured, nursed backIf sick, killed & replaced, not healed
IPs hardcoded in target groupAuto-registered/deregistered by ASG
Scale = you launch a new boxScale = change a number / a policy fires

Your servers stop being individuals you care for and become a herd defined by a template. This is the cloud-native shift.

The three pieces of an ASG

  1. LAUNCH TEMPLATE - the "cookie cutter": AMI, instance type, SG, IAM role, and a user-data script that boots the app on startup. Every instance ASG creates is stamped from this.
  2. AUTO SCALING GROUP - the controller: "Keep N healthy instances across these private subnets, registered to this target group."
  3. SCALING POLICY - the rule for N: "If avg CPU > 60% for 3 min, add an instance; if < 20%, remove one." (Target-tracking.)

How this rewires what you already learned

You learned (Layer)How ASG uses it
Target group (Layer 2)ASG auto-registers each new instance's private IP into the target group, and deregisters on termination. You never touch IPs again.
Health check (Layer 4)ASG uses the ALB health check to decide "is this instance healthy?" An unhealthy instance is terminated and replaced - self-healing.
Immutable Image (Layer 5)The launch template's user-data does docker pull <image> - the exact tested artifact. Scaling = launching more copies of the same image.

The one subtlety that trips people: how does a brand-new ASG instance get the app?

Two models - this is a real design decision:

A. BAKED AMI (immutable infra) - Pre-build an AMI that already has Docker + the image. Launch template just starts it. Fast boot, no deploy-time dependencies.

B. USER-DATA bootstrap - Launch template's user-data script runs on first boot: install Docker, docker pull the image, docker run. Slower boot, more flexible.

Your Ansible-based deploy fits a hybrid: bake Docker + agents into the AMI, let user-data pull the current image tag. The health check then gates the new instance into the target group exactly as before.

Breadth Deliverable - ASG via Console / CLI (no Terraform)

The 3 objects to create, in order:

1. Launch Template (The cookie cutter)

Application - The Observability Concept

The core question observability answers: "Is the system healthy, and if not, where and why?" You already built the first primitive - the health check. Observability scales that from "one yes/no probe" to "continuous, queryable insight."

The observability triangle (three pillars)

METRICSLOGSTRACES
Numbers over timeDiscrete event recordsOne request's journey
"CPU 70%, 5xx=12""ERROR: DB timeout"across all services

Metrics tell you something is wrong (and trigger alarms). Logs tell you what exactly happened. Traces tell you where in the request path it happened. For your project, CloudWatch gives you metrics + logs + dashboards + alarms out of the box.

The Four Golden Signals (what to actually watch)

Google's SRE framework - memorize these; they're the "what to monitor" answer graders want:

SignalQuestionYour metric
LatencyHow slow?ALB TargetResponseTime
TrafficHow much demand?ALB RequestCount
ErrorsHow often failing?ALB HTTPCode_Target_5XX_Count
SaturationHow full?EC2 CPUUtilization, Memory

The metrics that matter for YOUR architecture (free from AWS)

  • From the ALB: HTTPCode_Target_5XX_Count -> app errors (golden: Errors), TargetResponseTime -> latency (golden: Latency), RequestCount -> traffic (golden: Traffic), HealthyHostCount / UnHealthyHostCount -> how many app servers are alive, RejectedConnectionCount -> ALB overwhelmed
  • From the ASG / EC2: CPUUtilization -> saturation = drives scaling, GroupInServiceInstances -> is the fleet at desired size?
  • From your APP (custom metrics you emit): cache.hit / cache.miss ratio -> is Redis actually helping? (ties to Layer 7)

That last one is special - you emit it from the app (Spring Boot Actuator + Micrometer already expose cache stats). A low cache-hit ratio means Redis isn't earning its keep. This connects observability directly back to the data-layer design you learned.

The alerting mental model

A metric alone is passive. An alarm watches a metric and acts when it crosses a threshold for a duration: ALARM: metric + threshold + period = action (e.g., 5XX count > 10 for 5 min -> send SNS -> email/Slack/PagerDuty)

Three alarms you'd set for this app:

  1. UnHealthyHostCount >= 1 for 2 min = an app server is down (self-healing may be in progress, but you want to know).
  2. 5XX count > 10 for 5 min = the app is erroring even on healthy hosts.
  3. TargetResponseTime > 2s (p95) for 5 min = latency degradation (maybe Redis down = every request hitting RDS).

Notice alarm #3 would catch a Redis outage - because losing the cache makes every read hit the slower RDS, and latency climbs. Observability lets you see your architecture's assumptions holding or breaking.

What the Maven Surefire plugin is

Definition - Surefire is the Maven plugin that executes your unit tests during the test phase of the build lifecycle. When you run mvn test or mvn package, Maven delegates to Surefire to find your test classes, run them, and produce reports.

Why it matters (the problem it solves) - Without it, "building" your JAR would just compile code. Surefire is the gate that says "compile succeeded AND every unit test passed" before an artifact is produced. In your Jenkinsfile, the Build & Unit Test stage relies on Surefire - if a test fails, Surefire fails the build, the pipeline stops, and no broken image ever reaches ECR. That is the first quality gate in your CI/CD chain (SonarQube and Trivy are the later gates).

Mental model - think of the build lifecycle as a conveyor belt:

compile ---> test (Surefire) ---> package ---> ...
             |                      |
             any test fails = belt stops = no JAR, no image

The two sibling plugins (easy to confuse):

PluginPhaseRunsNaming convention it looks for
Surefiretestunit tests (fast, isolated)*Test.java, Test*.java, *TestCase.java
Failsafeintegration-test / verifyintegration tests (slower, real deps)*IT.java, IT*.java

Failsafe exists so a failing integration test doesn't abort the build before cleanup runs - it reports at the verify phase instead. For your project, Surefire is the one that matters right now.

A subtle point worth knowing - Spring Boot's parent POM already pulls in Surefire transitively, which is why mvn test works even though you never declared it. So "adding it" really means declaring it explicitly to pin the version and configure it (reports, which tests to include, fail-fast behavior) - making the build reproducible rather than relying on whatever version the parent happens to inherit.

What you just gained with the three plugins in pom.xml

Command/PhaseWhich plugin firesProduces
mvn testtest (Surefire + JaCoCo prepare-agent + report)test results + target/site/jacoco/jacoco.xml
mvn verifyintegration-test, verify (adds Failsafe)integration-test results
mvn packagepackage All above, then fat-jartarget/ecommerce-1.0.0.jar

Key invariant to remember: JaCoCo's prepare-agent must run before Surefire, which is why it binds to the lifecycle early - it instruments the JVM so that when Surefire runs your tests, coverage is recorded. The report execution then runs after, writing the XML that SonarQube reads.

One connection worth making to your Jenkinsfile: Your SonarQube stage can now point at the JaCoCo report: -Dsonar.coverage.jacoco.xmlReportPaths=target/site/jacoco/jacoco.xml. That's the thread that ties Surefire + JaCoCo -> the SonarQube quality gate into one unbroken chain: tests run, coverage is measured, and Sonar can fail the build IF coverage drops below your gate's threshold - exactly the "no broken image reaches ECR" principle from Layer 5.

Jenkins slave mental model (The single most misunderstood part of CI/CD)

The Jenkins slave does almost everything itself. It does NOT "forward" the code to the SonarQube, Trivy, or Maven servers. Instead, the slave runs client tools that reach OUT to those servers over the network and send them data. Let me correct the mental picture, because the phrase "forward the code to the Maven/Sonar/Trivy servers" hides the real architecture.

The key reframing: "Server" means two very different things here

ThingIs it a place code gets sent to?What actually happens
"Maven server"❌ NoMaven is a tool installed on the slave. The slave runs `mvn` locally on the code it checked out. (A "Maven server" usually means Nexus/Artifactory - a repo the slave downloads dependencies from and uploads the built jar to.)
SonarQube server⚠️ PartlyThe slave runs the sonar-scanner client locally, which analyzes the code and sends the analysis results (not the raw repo) to the SonarQube server, which stores them and computes the quality gate.
Trivy❌ Mostly NoTrivy is a scanner tool the slave runs locally on the built image. It only reaches out to a server to download its vulnerability database.

So the real flow is "the slave is the worker; the servers are services it calls." Nothing gets "handed off" to be processed elsewhere - the slave orchestrates everything from one working directory.

The mental model: A chef in a kitchen

graph LR subgraph Jenkins Slave "The Chef's Kitchen (one working directory holds ALL the code)" Code[Git Clone] Mvn[mvn package runs locally] Sonar[sonar-scanner runs locally] Trivy[trivy image runs locally] Code --> Mvn Code --> Sonar Code --> Trivy end Nexus[Nexus Maven server] SonarServer[SonarQube Server] TrivyDB[Trivy DB Server] Mvn -->|calls out to pull deps/push jar| Nexus Sonar -->|sends analysis to| SonarServer Trivy -->|pulls CVE DB from| TrivyDB

The chef (slave) never ships the raw ingredients (code) to another kitchen. The chef uses tools and phones out to suppliers (servers) for ingredients and inspections.

"What makes it know which tasks and where the servers are?"

  1. WHICH tasks, in what order -> the Jenkinsfile: Your Jenkinsfile is the recipe. Each stage { } is one task, and they run top-to-bottom. That's the only thing deciding what gets done and in what sequence. Jenkins reads this file from your git repo.
  2. WHERE the slave runs -> the agent directive + Jenkins labels: When you register a slave, you give it a label (e.g. linux-builder). In the Jenkinsfile you write agent { label 'linux-builder' }. Jenkins' master matches the label to a registered node and dispatches the whole pipeline there. That is how "the code lands on the slave."
  3. WHERE the external servers live -> credentials + URLs, NOT hardcoded in logic: The slave needs the address of SonarQube, Nexus, etc. These come from Environment variables / config (SONAR_HOST_URL, the Nexus URL in your pom.xml <distributionManagement>) or Jenkins Credentials store injected via withCredentials. So the slave "knows where SonarQube is" because the Jenkinsfile hands sonar-scanner a -Dsonar.host.url=https://sonar.internal:9000. There's no magic discovery - it's configuration.

Tying it to the network layers: For the slave to reach these servers: Slave SG -> outbound to SonarQube SG on :9000, Nexus on :8081, ECR on :443. Each server's SG has an inbound rule sourced from the slave's SG (the SG-references-SG pattern you nailed in Layer 3).

Application Code Logic: Redis & S3

Question 1: How do app servers reach Redis for their queries?

Here's the surprise that trips everyone up: there is no line of code in ProductService that says "connect to Redis" or "query Redis." That's the whole point of Spring's abstraction. Reaching Redis is split across three places - config, enablement, and a single annotation.

Piece 1 - WHERE Redis is (the address) -> application.yml

data:
  redis:
    host: ${REDIS_HOST:localhost}  # <- line 29: the Elasticache endpoint
    port: ${REDIS_PORT:6379}       # <- line 30
cache:
  type: redis                      # <- line 32: "use Redis as the cache backend"

This is the only place the Redis location lives. In production you set REDIS_HOST=my-cluster.xxxx.cache.amazonaws.com as an env var (via Ansible/the container run command), and the same image points at the real ElastiCache. That's the immutable-image principle. Spring Boot reads these properties at startup and auto-builds a RedisConnectionFactory - the actual TCP client to Redis on port 6379.

Piece 2 - Turn caching ON -> EcommerceApplication.java (@EnableCaching)
Without @EnableCaching, the @Cacheable annotation is inert - Spring ignores it. This annotation installs the proxy layer that intercepts cached method calls.

Piece 3 - WHEN to reach Redis -> ProductService.java line 29

@Cacheable(value = "products", key = "#id")  // <- THIS line is the Redis query
public Product getProduct(Long id) {
    return repository.findById(id).orElse(null);  // <- this hits RDS (only on MISS)
}

This single annotation IS the Redis interaction. Here's the exact mechanism, step by step:

Someone calls productService.getProduct(42)
  |
  v
Spring's caching PROXY intercepts the call BEFORE your method body runs
  |
  |-- builds the key "products::42"
  |-- sends GET products::42 ---------------> REDIS (port 6379)
  |
  -------------------------
  | HIT                   | MISS
  v                       v
returns cached Product  runs your method body:
your method NEVER runs  repository.findById(42) --> RDS (port 3306)

                        (with the 5-min TTL from line 34)

The precise answer to "how do app servers reach Redis":

  • The TCP connection is created by Spring Boot at startup from the application.yml host/port.
  • The decision to talk to Redis happens inside the caching proxy that @Cacheable installs.
  • Your code never writes redis.get(...) - Spring writes that plumbing for you. The annotation is a declaration ("cache this"), and the framework turns it into the actual GET/SET network calls.

The write side keeps the cache honest - ProductService.java line 57:

@CacheEvict(value = "products", key = "#product.id")  // sends DEL products::id to Redis
public Product saveProduct(Product product) {
    return repository.save(product);                  // writes to RDS
}

When a product changes, @CacheEvict fires a DEL to Redis so the stale copy is removed; the next read MISSes and repopulates from RDS.

Question 2: How does S3 serve product images, and how do they get matched to the right product?

The key insight: the image bytes never pass through your app server. The app only hands out a link. Here's the full stitch, traced through four files.

The link that joins a product to its image: imageKey. The matching happens through one field on the Product - Product.java line 30:

private String imageKey;  // e.g. "iphone15.jpg" - the S3 object key

This string is stored in the RDS row right next to the product's name and price. So RDS already knows "product 42's image is the S3 object named iphone15.jpg." That's the join - the product record carries the filename of its own image.

The full stitch, step by step through the code:

  1. Request arrives -> ProductController.java line 42: @GetMapping("/{id}") public ResponseEntity<Map<String, Object>> one(@PathVariable Long id) {
  2. Fetch the product info (via Redis/RDS from Question 1) -> line 43: Product product = productService.getProduct(id); (Now the app holds the product, including product.getImageKey() = "iphone15.jpg").
  3. Turn the key into a temporary S3 URL -> line 50: body.put("imageUrl", s3Service.getImageUrl(product.getImageKey()));. This calls into S3Service.getImageUrl() line 42, which takes the bucket (from application.yml) + the imageKey, builds a pre-signed GET URL valid for 10 minutes, and returns something like https://ecommerce-product-images...
  4. Respond with product info + image link -> line 48-50. The JSON the browser receives:
    {
  "product": { "id": 42, "name": "iPhone 15", "price": 999, "imageKey": "iphone15.jpg" },
  "imageUrl": "https://ecommerce-product-images.s3.amazonaws.com/iphone15.jpg?X-Amz-Signature=..."
}
  5. The browser fetches the image directly from S3. Your HTML would do <img src="{imageUrl}">. The browser makes a separate request straight to S3 - your app server is completely out of that path.

Why pre-signed URLs (the "why" behind the design):
NAIVE way: Browser -> App server -> downloads image from S3 -> streams to browser (app server wastes CPU/bandwidth proxying bytes; slow, doesn't scale).
THIS way: Browser -> App server -> gets a signed URL (tiny string). Browser -> S3 directly -> image bytes (app only hands out a link; S3 serves the heavy bytes).

And the credentials for signing come from the IAM role, not keys - S3Service.java line 37: .credentialsProvider(DefaultCredentialsProvider.create()) // uses the EC2 instance's IAM role. No access keys anywhere in the code - the app server's attached IAM role grants s3:GetObject, and the SDK picks it up automatically.

The complete picture - RDS and S3 collaborate:

graph TD RDS[RDS row 42: name:'iPhone 15', price:999, imageKey:'iphone15.jpg'] App[product.getImageKey] S3Service[S3Service signs] S3Obj[S3 object: s3://ecommerce-product-images/iphone15.jpg] URL[pre-signed URL] Browser[Browser fetches bytes from S3] RDS -->|reads info & imageKey| App App --> S3Service S3Service --> URL S3Obj -.->|bytes served directly| Browser URL -->|gives src=...| Browser

RDS holds the info and the filename; S3 holds the bytes; the imageKey field is the glue. The product and its image are matched because the product row literally stores the name of its own S3 object.
